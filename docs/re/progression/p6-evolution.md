## P6.1 Town evolution
- **Data.** Species record (0x48 bytes): `+0x34` pre-evolution species (s16), `+0x36` method (u16), `+0x38` parameter (s16), `+0x3A` extra condition (u16); `020020C8` copies the four. Methods: 1 level, 2 IQ, 3 item, 13 none (needs only the extra condition's item); method 0 with a pre-evolution is only produced by the Ninjask case. In `crates/data/src/species.rs` the names are stand-ins: (pre, method) and (param, cond).
- **Check** `0200475C(rosterRec, out, hasItemsGiven)` on the roster record, for each species `s` whose pre-evolution is the member and whose method is nonzero: (1) the area of `s` must be owned (else flag `0x20`) and have room (count below capacity, the member's own slot freed when the area is shared; else `0x40`); (2) method 1 blocks below the level (flag 2), method 2 blocks below the IQ (`0x10`), method 3 needs the item among the two offered or in the 20-slot bag (`02007AF8`; else `0x08`); (3) the extra condition: 4 needs one item, 8, 9 and 10 each another, 5 needs attack above defense, 6 defense above attack, 7 equal (the Tyrogue line), 11 and 12 depend on a random byte (`out[2] & 1`, from `02011968(0xFF)` drawn at each menu check on the ARM9 generator, so re-rolled at each check; the Wurmple line); (4) unblocked sets flag bit 0 and the target; the last unblocked species wins. No candidate gives flag 4.
- **Apply** `0200468C` then `02004590`: copies the record, sets EXP to the table value of the new species at the same level, writes the new species, records the evolution level at `+8` (or `+9` if `+8` is used; `020017D0` reads these for the learn chain), renames only when the nickname equals the old species name, inserts through `02003130`, clears the old slot, removes the offered items from the bag. Level, IQ, skill bits, moves and stats carry over; no stat recompute was seen. **Ninjask** (species 316) also builds a Shedinja (317) record if a roster slot exists.
- **Condition item names** [emulator-verified, ROM read of the `itempara` entries in `system.sbin`, NitroFS file id 167, entry stride 0x20; sanity: id 1 is "Stick", #573]: extra condition 4 needs item 0x76 (Link Cable), 8 needs 0x30 (Sun Ribbon), 9 needs 0x31 (Lunar Ribbon), 10 needs 0x2F (Beauty Scarf). The item-name readers `02009040`, `020090D0` and `0200B188` and `message_e.str` are not this table. Method 3 uses the species parameter `& 0xFF` as its item id (`0200475C`, static); the per-species parameter list was not extracted, so no per-species item names are given.
- **Menu** [blue-verified, static literal reads at `02048464` to `020484B4` plus ROM read of `message_e.str` file id 149, #573]: state machine `02047D74` (entered from `020485D8`) is the evolution menu. It calls `0202F280` and `0202EDF0` with message ids 0x74F to 0x753, 0x757 to 0x75E and 0x760. A #619 ARM decode of the retail code dump also finds 0x74D at literal `0204845C`: state 0 loads it at `02047E68` and calls `0202EDF0` at `02047E70`; state 1 similarly uses 0x74E. Thus 0x74D is statically the first menu message [blue-verified static, #619], but its actual runtime display is unconfirmed. **The title in this EUR dump is "Luminous Cave"** (message 0x74D, [blue-verified, ROM read of `message_e.str` file id 149]); the text "Luminous Spring" is not in this dump. So the "Luminous Spring" name is **refuted for EUR** and unverified for other regions; no US dump was available for the #619 check.
- **Town runtime** (`0200475C`, `0200468C`, `02004590`, `02047D74`) [#639, partly reached, emulator-verified]: the Luminous Cave (map 8, `MAP_LUMINOUS_CAVE` in pret/pmd-red) is where the evolution menu runs. ## P6.2 Dungeon evolution (wild monsters)
- **Trigger.** `0217D5FC` sets `info+0x11B = 1` and `gDungeon+0xD = 1` when the attacker is **not** a team member and `02006130(gDungeon+0x63C)` is nonzero. `02006130(id)` returns the byte at `0x02092818 + id*0x10 + 1` [blue-verified static, `02006130`, literal `02006134`]. `02183BB4` then acts if `gDungeon+0x10 == 0`.
  - **Dungeon rows** [emulator-verified, #573, scratch ROM, 300 frames]: the byte is 0 for every id `0x00` to `0x61` (full loop; the dungeon names of ids 0x00 to 0x61 are read through `0x02093588`). The nonzero rows start at id `0x62`; they are the status and move-name table that shares the `0x10` stride (its names are read through `0x02093588`), not dungeon rows. So the wild path does not fire in any retail dungeon. The earlier note "the table has nonzero bytes in later rows" was this status table.
  - **Dungeon id source** [blue-verified static, ARM decode of the retail code dumps, #619]: `gDungeon+0x63C` is the requested dungeon id, written by `0206DE4C` or `0206DE64`; the latter forces floor 1. No writer of an id `0x62` or greater was found in ARM9 or the overlays, and range checks at `0206D450`, `020061AC`, `020061D8` and `02006318` treat `0x61` as the last dungeon id. The source request structure was not traced and no runtime id range was captured, so an out-of-range runtime value remains unobserved rather than disproved.
  - **Writers of `info+0x11B`** [blue-verified static, ARM immediate-offset store scan of ARM9 and all 145 overlays, #619]: the only nonzero store is the wild/non-team store of 1 at `0217E7BC` in `0217D5FC`. The other direct stores clear it: `0217976C` (spawn init `021794CC`), `021836D8` (`02183644`), `02183B58` (`02183994`), and `02183F38` (`02183BB4`, from a stack slot initialized to zero on the decoded path). The quicksave code reads it at `0219B338` and writes the saved byte at `0219BB1C`; `0219977C` is a stack copy, so save/restore only round-trips an existing value. No team-member writer was found. This does not exclude a computed-offset write or a whole-record copy.
- **Target.** `02001738(species, buf, 0, 0)` lists species whose pre-evolution is the current species and, with `param_3 == 0`, whose body size (species byte `+9`) equals the current one; it does not check method, level, IQ or item. With `n` candidates, one `DungeonRandInt(n)` draw picks a start, then a forward scan with wrap finds the first candidate that is in the floor's species list (`021389A0`) and has a loaded-sprite pointer (`02178C04`). The scan draws nothing. [blue-verified, disassembly for the argument]
- **The `02178C04` result** [blue-verified static, ARM decode of the retail code dumps, #619] is `*(u32 *)(gDungeon + 0x158DC + species*4)`, a 0x1A8-entry per-species array of loaded sprite/animation pointers, not a per-floor data table. `02178B9C` fills an empty slot by formatting `ax%03d` and loading it through `0201A54C`; `02178CB0` clears the array and loads species 0x1A5, the floor monster list, team members and special records, while `02178C4C` reloads live-entity species. Apply calls it at `02182938` and uses the result as the evolved form's sprite. Therefore forcing `021389A0` does not populate the target's pointer: the forced zeros for 159, 5, 291, 293 and 192 are unloaded-sprite slots. Their absence from that floor's loads is the static explanation; direct runtime reads of slots 158/4/290 (expected nonzero) and 159/5/291 (expected zero) remain open.
- **Apply** `02182900`: `info+4 = info+2 = c`, EXP set to the table value, `0217930C` re-derives types and abilities, animation and messages; level, HP, IQ and moves stay. Target 316 also spawns 317 next to the entity when 317 is on the floor list. A team member gets its stat deltas (`02183720`) afterwards. The #619 decode puts the 316 test at `021829B0`; `02182A70` is inside that branch after `021389A0(317)` at `02182A10`, so it cannot be a common apply-return hook and a forced 316 run must also pass the 317 check. `02182A74` is the common join used by the updated probe for after-apply snapshots [blue-verified static, #619].
- **Runtime, forced** (#573, probe `verification/v7-trace/evolution_probe.py`, see [verification.md](../../verification.md#573--dungeon-evolution-trace-forced-run)): on the first floor of a new game, with `+0x11B = 1` and `gDungeon+0xD = 1` poked on every entity, `02183BB4` runs with `gDungeon+0x10 = 0`, and `02001738` gives candidate lists that `DungeonRandInt` draws from: hero species 158 gives 1 candidate, partner 4 gives 1, wild 290 gives 2 [emulator-verified]. Apply runs only when `021389A0` (floor list, return at `02183DE0`) and then `02178C04` (loaded-sprite array, return at `02183DF8`, and again inside apply at `0218293C`) return nonzero. **With both forced to 1**, `02182900` runs for 158 to 159, 4 to 5 and 290 to 291 [emulator-verified, forced]. Level byte unchanged; `+0x11B` cleared on the hero and partner. **Natural path** (no return forcing; earlier scratch run, not re-run with the committed probe): `021389A0` returns 0 for every candidate, so `02178C04` is not reached and apply does not run on this floor [emulator-verified, natural]. **With only `021389A0` forced to 1**, `02178C04` (lr `02183DF8`) returns 0 for every candidate (159, 5, 291, 293, 192) [emulator-verified, forced]. So once the floor check passes, the loaded-sprite check is what stops apply on this floor; the static reason is above.
