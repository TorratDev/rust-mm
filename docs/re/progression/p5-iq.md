# P5. IQ [blue-verified, static]

Part of [Progression](../progression.md). Addresses are `ov_0001::` unless plain (ARM9).


- **Stores** (all s16): roster record `+0x0A` (10 bits in the save), party record `+0x06`, entity info `+0x0C`. New hero and partner (`02003510`) and a recruit start at IQ 1. The ally spawn (`02179990`) copies party to entity; `02179128` writes back.
- **Only gain: gummis** `02145EC8(user, target, gummiType)`. For a team member whose `+0x40` is not `'J'` or `'G'`: `IQ += T[type1][gummi] + T[type2][gummi]` over the target's two types (`info+0x56`, `+0x57`), clamped to 1 to 999; then `021804CC` and `02175E60` (messages for newly unlocked skills). The IQ table is 18 x 18 s16 at `02092308`; a second table at `02092590` (same shape) drives belly. Tables not copied. Level-up, evolution and recruiting do not change IQ.
- **Unlock** `02004464(iq, skill) = skill != 0 && threshold[skill] <= iq`, `threshold` being 24 words at `02091F48`. `02004404` lists all unlocked skills. Skill names are in the name table below ([blue-verified], string-read).
- **Correction to [`structs.md`](../structs.md):** a set bit in `+0x84..+0x86` means the skill is **enabled** (the player's on/off choice), not blocked. Evidence: `021804CC` sets bit `n` of `+0x87` when `02004464(IQ, n)` and `02004250(info+0x84, 1<<n)` are both true; the default writer `0200429C` sets bits 2, 3 and 22 (and 18 if its flag is nonzero); `0200439C` toggles. The same 24 bits are the roster `+0x18` and party `+0x42` fields shown by the IQ menu.
- **Active skills** `+0x87..+0x89` = unlocked AND enabled, rebuilt from scratch by `021804CC` (callers include the gummi, spawn `02179990`, `021833BC`, `02183120`). Wild monsters ignore IQ: a fixed set of bits, plus bit 18 when `+0xD4` is nonzero and bit 22 when the level reaches a cap read from `021AA1F8`.
- **Exclusive groups.** `020042F8(p, n)` sets bit `n` after clearing every bit with the same group id; the group array (24 words) is at `0208FA84`. Seven groups of two to four skills; the others stand alone. Enabling one skill switches off its group mates.
- **Partner at start:** IQ 1, enabled and active {2 Item Catcher, 3 Course Checker, 22 Item Master}; skills 21 Dedicated Traveler and 23 Exclusive Move-User are unlocked at IQ 1 but off by default.
- **IQ persistence at dungeon exit** [blue-verified; runtime with a forced call]: `02178068` → `02001E24` → `02001D24` copies party `+0x06` (IQ) to roster `+0x0A`, and party `+0x42..+0x44` to roster `+0x18..+0x1A`. `02001E24` is entered with r0 = party index (`+8`) and r1 = party record; it tail-jumps to `02001D24`, whose entry has r0 = roster record (`*020DDF84 + idx*0x40`) and r1 = party record (party base `*020DDF84 + 0x6740`, stride `0x54`). Runtime (`verification/v7-trace/iq_persist_probe.py` on pmdb.nds, SHA-1 `6f01887356268de39085df01490347bbcc3aa330`; command `~/venvs/desmume/bin/python verification/v7-trace/iq_persist_probe.py <ROM> <OUT.json> --force-call`; output SHA-256 `b45616155588fbe3f3ab3319a598ca5ffd46c06674784ea7c9ebf6fb3704f636`): sentinel IQ 564 and skill bytes `0x11, 0x22, 0x33` were written to the leader's party record; `02001E24` was hit for both party records (leader r0 = 54), and `02001D24` after it for both. The leader's copy reached roster record `0x020E1D0C` (idx 54): roster `+0x0A` = 564, `+0x18..+0x1A` = `0x11, 0x22, 0x33`. The partner's record (IQ 1, bytes 12, 0, 64) reached `0x020E43CC` with the same offsets. **Caveat:** `--force-call` sets r0 = 0 and jumps to `02178068` at the first turn-loop trigger (`0x021411BC`), so the entry is forced; the natural floor-exit trigger was not driven. **Not verified:** that trigger (`FUN_0206dc20` calls at `0206ED24`, `0206ED3C`, `0206ED4C`), and whether the other copier `02001CD8` copies the same fields.
- **Dungeon exit copy (#588) [blue-verified, static; no runtime run].** `ov_0001::02178068` (exit commit, see "Where a recruit goes") copies each valid party slot (bit 0 of the u16 at `+0`) whose `ov_0001::02176368(party +8)` is 0 and whose `ov_0001::02176344(party +8)` is nonzero (a range check; the bounds are in the Gate bounds bullet below). The copy depends on `FUN_02006444(gDungeon+0x63C)` (ARM9 `0x02006444`, called from `02178068` at `021781C0`; the two copy calls are at `021781E4` and `021781D4`):
  - **Zero:** `02001E24` (call `021781E4`), a wrapper of `0x02001D24` through the pointer at `0x02001E3C`, with the roster base `0x020DDF84`. Copies the whole party record: IQ (party `+0x06` to roster `+0x0A`), the skill-enable bits (party `+0x42` to `+0x44` to roster `+0x18` to `+0x1A`), and the held item (party `+0x36`, flag bit 0, to roster `+0x1C`; 0 if the flag is clear).
  - **Nonzero:** `02001CD8` (call `021781D4`). Copies only the held item, with the same flag rule (party `+0x36` to roster `+0x1C`). IQ and the skill bits stay as they were in the roster.
  - **Table.** `FUN_02006444` is `ldrb r0,[r1,r0,lsl #4]` (element size `0x10`), with `r1` loaded from the literal at `0x02006450`. That word is a pointer, `0x0209281E`, which is record `id`'s `+6` in the dungeon table at `0x02092818` ([structs.md](../structs.md#dungeon-data-table-170-p1b)). So the decompile's `DAT_02006450 + id*0x10` names the pointer, not the table.
  - **Dungeon ids with a nonzero byte: `0x1A`, `0x3A`, `0x3E`** (decimal 26, 58, 62). Ids `0x00` to `0x61` are the dungeon records; from `0x62` on the rows have another layout and are not read as dungeon flags. Every other id in `0x00` to `0x61` is zero, so those dungeons copy IQ to the roster at exit. No name for these ids is in the repo ([data.md](../../formats/data.md): dungeon names are in the message tables, not mapped), so they are given by id only.
  - **Xrefs** (export `xrefs.tsv`, [blue-verified]): `FUN_02006444` is called from `02178068` at `021781C0`, from `ov_0001::021778F4` at `02177C44` and `02177E68` (zero calls `02001E24`; no `02001CD8` in that function), from `ov_0001::02178828` at `021788C4` (nonzero calls `020033A8`, not the copy), and from ARM9 `0206DC20` at `0206DF84` (not read in detail).
  - **Gate bounds (#595)** [blue-verified, static; the word values were read from the ov_0001 image in the rescue-arm9 bridge and were not re-read in this pass]:
    - `ov_0001::02176344` (export `ov_0001/02176344_*.c`) returns 1 iff `-1 < id < word@ov_0001::02176364` (literal read at `ov_0001::0217634C`). That word is **413**, so the copy admits ids `0` to `412`. **413 is the roster record count** [verified: static loop bounds plus the emulator count]. The roster loops use 413 as the bound with stride `0x40` at the roster cell: `02005A0C` (`DAT_020060B0`), `02178828` (`DAT_02178A78`) and this gate (`02176364`). The emulator count in "Record base" is 413 too. The same number also appears as the learn cap (`DAT_02001A2C`) and the move-effect case count, so the value alone does not name the roster; the role comes from the loops. The species table count was not read. The party `+8` field is used as the roster index: `02001CD8` and `02001E24` index the roster at `id * 0x40` [blue-verified use]. No writer of `+8` was read, so its meaning is [red-hypothesis].
    - `ov_0001::02176368` (export `ov_0001/02176368_*.c`) returns 1 iff `id == word@ov_0001::02176390` or `id == word@ov_0001::02176394` (literal reads at `ov_0001::02176368` and `ov_0001::02176378`). The two words are the constants `0x55AA` and `0x5AA5`. Both are outside `0` to `412`, so a sentinel id always fails `02176344`. [blue-verified from the control flow.] Readers and writer [blue-verified, static]: `02176368` tests the words at `02176390` and `02176394`. `02176398` returns 1 for `0x55AA`, `0x5AA5` or any negative id. `02179128` reads `0x55AA` from `0217926C` and `0x5AA5` from `02179270`: when a team entry's id is `0x55AA`, it writes `0x5AA5`. The writer is `0217855C`, which adds a member to an empty team slot when the team total is below 7, by calling `02001E40(slot, src, 0x55AA)`. That call stores the third argument at team `+8`. The only literal-pool occurrences of the two words in `arm9.bin` and the overlays are in `ov_0001`. Two more occurrences (`02179384`, `02179394`) have no reader. Meaning: [red-hypothesis] temporary team members whose id is not a roster index. `02178068` skips the copy-back for them (its gate needs the sentinel test to be 0).
    - Gate in `ov_0001::02178068` (export lines 39 to 70; copy calls at lines 65 to 70): copy iff slot bit 0 is set, `02176368(id) == 0` and `02176344(id) != 0`. The sentinel test therefore does not change which ids are copied. It only decides the mark branch: with `02176344(id) == 0` and a nonzero argument, a non-sentinel id is marked in `local_1e0`, and a sentinel id is not. [blue-verified from the control flow.]
  - **Level-1 reset and exit effect (#603)** [blue-verified, static]:
    - **Entry.** `FUN_0206DC20` (run setup) calls `02178828` at `0206DEF8`. In its `cVar2` branch it calls `FUN_02006444(gDungeon+0x63C)` at `0206DF84`, and when that is nonzero it calls `02003320` on the setup member. `02178828` loops over roster slots with flags bits 0 and 1 (at most 4). It copies each roster record into a team entry through `02001FA8`, which tail-calls `02001E40`. When `02006444` is nonzero it builds a member with `020033A8(buf, species, 0, 0, …, 0)`. `020033A8` and `02003320` both set the level word `+0xA` to 1 and recompute the stats from the species. `02178828` then copies the build into the team entry (team base `roster base + 0x6740`, stride `0x54`): buf `+0xA` (level) to team `+6`; buf `+0xC` (stat word) to team `+0xE` and `+0x10` (current and max); buf `+0xE..0x11` to team `+0x12..0x15`; buf `+0x18..0x1B` to team `+0x42..0x45`; and the move block (buf `+0x1E`) through `0200978C` at team `+0x1C`. Team `+0xA` is set to the slot number, and unused slots `n..3` get `+0x6740 = 0`. The buffer offsets come from the decompile's stack-slot names (`local_XX` is frame offset `XX`), so they are consistent with the `020033A8` writes but not checked in the disassembly.
    - **Exit.** `02178068` calls `02001E24(id, slot)` when `02006444` is zero, and `02001CD8(id, slot)` when it is nonzero. `02001E24` tail-calls `02001D24`, which copies the whole team entry back into the roster record, level included. `02001CD8` copies only the held item: the flag is bit 0 of team `+0x36`, and the two bytes at `+0x37` and `+0x38` go to roster `+0x1C` and `+0x1D` (`FUN_02008314`). With the flag clear it zeroes roster `+0x1C`. So with the byte nonzero the roster level is never overwritten, and it comes back as it was before entry.
    - **Verdict.** Byte `+6` nonzero gives level 1 in the dungeon and keeps only the held item on exit. This is static. The in-game result is not run, tracked in [#589](https://github.com/TorratDev/rust-mm/issues/589).
  - **Not checked:** the third argument of the `02001FA8` tail call (it sets team `+8`, which `02178068` reads as the roster index; the decompile does not show it), and the runtime checks of the level-1 entry and the dungeon-id copy (no probe run; [#589](https://github.com/TorratDev/rust-mm/issues/589)). Byte `+6` is covered in [structs.md](../structs.md#dungeon-data-table-170-p1b). The IQ result at runtime is in the IQ persistence bullet above.
- **Not verified:** the meaning of `+0x40` `'J'`/`'G'`, the flag argument of `0200429C` at the roster-creation sites.
- **Sim:** per member IQ (1 to 999) and a 24-bit enabled mask; derive the active bits when either changes.

**Skill names.** Evidence: the u16 table at `02092FC4` holds `0x394 + n` for skill `n` (n = 1 to 23; entry 0 is "no skill"). Reader `0200457C` returns entry `n`. The text lookup `0201D948` takes bank id `id - 1` (string offset `(id - 1) * 4`, bit 15 clear), so each name is the English message-bank string at that id. Every row is **[blue-verified]** (string-read; the in-game lookup was not run). This confirms names and ids, not the effect of each skill. Index 18 is named: Self-Curer (row 18, [blue-verified], string-read). Index 0 is not a skill; it means "no skill" and has no name row.

Source for reproduction: English `message_e.str` in the EUR APHP ROM (NitroFS file id 149). The strings were read statically from the `.str` offset table (entry `id - 1`, string to the next NUL). The table at `02092FC4` was confirmed two ways: a static decompile of the literal at `0200458C` (the pointer `0200457C` loads), and a runtime read in py-desmume on a scratch copy of the ROM. No probe script or table dump is committed; a reader repeats the check from the ROM's NitroFS and the `0200457C` decompile.
