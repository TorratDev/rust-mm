# P4. Friend areas [blue-verified, static; runtime results tagged blue-verified runtime, the rest unverified]

Part of [Progression](../progression.md). Addresses are `ov_0001::` unless plain (ARM9).


- **Species to area.** Species record byte `+0x16` (reader `020022DC`, [blue-verified static]) is the area id (0 to 57). Byte `+0x12` (reader `02002288`, [blue-verified static]) is the friend flag: eleven species have it nonzero, and they pass the recruit gate without their area (P3 gate 4). **Runtime: unverified.** The last attempted reader-pointer chain (`*(*020022A0)` for the flag and `*(*020022F4)` for the area) produced `0x06609AD0`, outside main RAM. The species table base is therefore unresolved, no runtime `+0x12` count is valid, and the count of eleven remains static-only. Record stride `0x48` and offsets `+0x12`/`+0x16` are static reader evidence. Meaning of the flag [red-hypothesis] "recruitable without the area".
- **Area table** at `02092138`: 58 entries of 8 bytes (no values copied; the shape and the readers are the note):
  - **Field 1, `s16` capacity at `+0`** [blue-verified static]: readers `02008EC4` (`02008EDC`, `02008F20`: running sum of capacities before an area) and `02009230` (`02009238` to `02009260`: roster index to area). Capacities sum to 413, the roster size (earlier static work).
  - **Field 2, byte at `+2`** [blue-verified static, reader `02009120`, callers `0200F4A8`, `0200FB8C`, `0204252C`, `02042618`, `020441CC`, `021A7140`]: the callers compare it with 0, 1, 2 and 3. `0200F46C` takes unowned areas with field 2 equal to 2; `02042578` takes unowned areas with field 2 equal to 0; `021A7124` drops unowned areas with field 2 equal to 2 or 3; `020424B0` (argument 2) returns 0 on field 2 equal to 0 and, on field 2 equal to 1, tests flag 6 (`0201F994(6)`); `02043C34` case `0x18` (`0204438C` record) branches on field 2 equal to 1 and the same flag test. Meaning: a class that decides which list an area is on [red-hypothesis]; names not known. **Runtime meaning unverified:** no probe compared field 2 with an identified game state or list.
  - **Field 3, `u32` at `+4`** [blue-verified static, reader `02009110`, callers `02042758` in `02042674` and `02042B70` in `02042AF4`]: `02042AF4` returns 3 after `FUN_02029A3C(2)` when the `u32` at `*DAT_020428E8+0x234` is below field 3; `02042674` takes the same comparison and shows a message instead. So field 3 is a cost checked against a stored value. "Price" and the name of the value at `+0x234` are [red-hypothesis]. `02009040` also reads the same `0x0209213C`-based literal (`02009064`, stride 8) as a number to format when its flag is 1 ([lead]: the literal's identity is not confirmed). **Runtime meaning unverified:** no purchase or list path compared field 3 with the stored value at `+0x234`.
- **Owned flags.** 58 bytes, one per area, at the base pointer `*020DED04` (read at `02009004`; area index = byte index). Reader `02009000`, setter `02009014` (both [blue-verified static]). No setter with a constant argument sets area 0 (see below).
- **Roster.** 413 entries of 0x40 bytes at `*020DDF84`, partitioned by area (area `a` owns `capacity[a]` slots after the running sum). Entry bit 0 valid, `+4` = `'A'` special, `+6` species. [blue-verified static, earlier work]
- **Setters of owned areas** (every `02009014` caller in the export, [blue-verified static]):
  1. **Bulk init:** `02069848` loops with `02009014` from area 1 while the counter is below 0x3A (areas 1 to 57; export lines 19 to 22, the call's own address is not in the decompile export) and inserts 300 roster records with `02003130`. Caller `020699B4` case 6 (call at `02069A5C`), reached from the dispatcher `020628BC` case `0x10` (call at `02062A98`).
  2. **Scripted** (dispatcher `ov_0000::02140860`, selected by its second argument; the event caller is not traced [lead]): mode `0x17` sets areas `0x0C` and `0x12` (`02140E88`, `02140E90`); mode `0x19` sets the area of species `0x51` (`02140EBC`); mode `0x1B` sets the area of a species from a literal (`02140F74`); mode `0x25` sets the area of a species from a literal only when it is unowned (`02141270`); mode `0x2C` sets the area of a chosen species (`0214172C`).
  3. **Map id to area:** `0201F8A8` sets the area that `0201F960` maps from an id (`0201F8D8`); called from the dispatcher at `021410E8`, from `ov_0000::02145494` (in `021421CC`), and through `0201F8E8` from `ov_0000::02145768` [blue-verified static; the map ids are not traced].
  4. **Join:** `ov_0001::0217F4CC` in `0217F388` sets the recruit's area ([blue-verified static], P3 join).
  5. **Recruit from list:** `ov_0001::0217F0F0` in `ov_0001::0217EF24` sets the area when the owned read (`0217F0E0`) is zero; caller not traced [lead on role].
  6. `ov_0001::021A79A4` in `021A75C0` sets an area from a picked value; role [lead].
  7. `02057B74`, `02057BA8` in `02057994` (state machine `02057E40`, case 3) set the area of a byte in the record at `+0x24`; role [lead].
- **Initial owned set at new game** [blue-verified runtime for the fresh-save first-floor path; bulk-init trigger unverified]: on a throwaway ROM copy with a fresh save, `boot_to_dungeon.txt` reached the first floor at frame 24960. The 58-byte owned table at `*020DED04` had base `0x020E7B6C`; only areas 9 and 26 read 1, and area 0 read 0. This is the observed owned set on that path; the earlier areas-1-to-57 starting-set claim is refuted here. `02069848`, `020699B4`, `02009014`, `02009000` and `02003130` did not run (exec hooks). The hero and partner insert `02003510` ran twice (frame 10743, return addresses `0x0201E070` and `0x0201E0E0`); its export (line 111) sets the owned byte of the copied record's area, a static account of areas 9 and 26. That attribution is not runtime write-watch evidence: the write watch on `0x020E7B6C+9` and `+26` was not run. Whether `02069848` runs on another path (post-tutorial or save creation) is **unverified**. The dispatcher `020628BC` was hit 56 times, but its state values were not logged, so state `0x10` is not confirmed on this path. The bulk setter's static loop remains setter 1 above, not an observed new-game result.
- **Where a recruit goes.** In the dungeon it is only a 0x54 party record. At the end of the dungeon `02178068` builds a per-area list: with room, each recruit is inserted with `02003130`; with a full area, a selection screen (`02175178`) makes the player release monsters (old ones or the recruit), then the survivors are inserted. `02003130` adds nothing if the area is not owned or its block is full, and marks the species seen (`020115BC`, [red-hypothesis]). A guard on entries with `+4` equal to `0x44` or `0x45` re-prompts; it is not understood (low).
- **Dungeon-end commit `02178068`** ([blue-verified static]; **runtime: unverified**). Its argument is a flag: 1 marks and inserts, 0 does neither (the mark and the insert are both behind `param_1 != 0`). The floor exit `0206DC20` calls it with the result code at its `+0x60`: codes 1, 2 and 4 call `02178068(1)` (`0206ED24`); code -2 calls `02178068(0)` (`0206ED3C`); code -1 calls `02177FD8` and then `02178068(0)` (`0206ED4C`); other codes do not call it here. The whole block sits inside `if (code == 1 || code == -2 || code == 4 || code == -1 || code == 2)` (export lines 592 to 602) [blue-verified static]. With flag 1, each party slot's recruit area comes from `020022DC` on the slot's species (calls at `021781F8` and `0217832C`; a 58-byte list marks the areas). The per-area list is built with `02009144` (`0217828C`) and counted with `02008EC4` (`021782A0`); the prompt text is `02009040` (`021783CC`); with a full area the selection screen `02175178` runs; inserts are `02003130` (`021783AC`, `02178508`). **Runtime, not reached:** no natural floor exit was driven. On the boot-to-floor run `0206DC20` ran once at frame 24952 (return address `0x0201DC64`) before `gDungeon` was set, so that call is dungeon setup, not an exit. `02178068`, `0206ED24`, `0206ED3C`, `0206ED4C` and `02177FD8` never ran (`friend_areas_probe.py`), so the flag per result code is unobserved. An exploratory run (not committed) wrote the leader's position onto the first floor's stairs at (23, 8) and walked it there; no exit ran. `combat_attack_inputs.txt` fights a monster and does not walk to the stairs. Still needed: an input script or driven state that walks the leader from its start (20, 25) to the stairs, or a forced `gDungeon+0x60` marked as forced.
